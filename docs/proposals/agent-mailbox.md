# Proposal: Agent Mailbox

**Status:** Proposal. Nothing is implemented.
**Audience:** Contributors working on the Go launcher, `tw-flow`, and the
collaboration protocol.
**Related:** [`ARCHITECTURE.md`](../ARCHITECTURE.md),
[`go-launcher.md`](go-launcher.md),
[`agnostic-conversation-window.md`](agnostic-conversation-window.md),
[`../tw-flow-session.md`](../tw-flow-session.md).

## Goal

An agent in any harness can send a message to an agent in another session or
another project, and the receiver sees it the next time it runs a workflow
command. Transport is files under the Jacazul home and a launcher command; no
harness API, socket, or terminal multiplexer is part of the core.

## Why

Two agents worked one feature across two projects: the launcher session
needed a library API from the flow engine session. Today there is no generic
channel between them:

- **Taskwarrior notes** are the record between agents, but each project has
  its own silo. A note in `jacazul-ai_launcher` never reaches the agent in
  `jacazul-ai_flow`, and silo isolation is a mandate, not an accident.
- **Harness channels** exist only in their harness. Claude Code can message a
  local session through a socket; Opencode, Copilot, and pi see nothing. That
  breaks the "Generic by Default" mandate in `AGENTS.md`.
- **`tmux send-keys`** wakes an idle agent, but it ties the exchange to one
  terminal, one pane, and one operator setup.

## Principles

1. **Generic by default.** Files and one `jacazul` command. Anything a
   harness or terminal adds is an optional adapter, and it states which
   harness it covers.
2. **Prompt as Ad delivery.** A pending message shows up as a banner in the
   workflow output the agent already reads (`tw-flow status`, onboard). No
   agent has to remember to poll.
3. **The record stays in Taskwarrior.** A message is transport. A decision it
   carries is written as a `tw-flow note` in the receiving project, with the
   receiver's signature. A mailbox is never the source of truth.
4. **A message is data, not authority.** It cannot approve a commit, a push,
   a task close, or an E2E run. Approval comes only from the operator in the
   receiving session.

## When an agent sends a message

```bash
jacazul mail send --to jacazul-ai_flow \
  --subject "Library API for opening storage" \
  --ref task:c3292d7b --ref ticket:#144 --body-file request.md
```

- `--to` is a project ID, optionally narrowed to a session:
  `jacazul-ai_flow/ba3be5c6`. Without a session, any session of the project
  may read it.
- The sender is filled in by the launcher from the resolved runtime:
  project, Jacazul session, persona, harness, and model. The agent does not
  type its own identity.
- `--body-file` follows the house rule for multi-line content: no bodies
  inlined in shell arguments.

## When a message is waiting

`tw-flow status`, `tw-flow session resume`, and the onboard prompt print one
line:

```text
📬 2 messages for jacazul-ai_flow (latest from jacazul-ai_launcher/0989a06c: "Library API for opening storage"). Run: jacazul mail list
```

The agent then runs:

```bash
jacazul mail list            # unread first, subject and sender per line
jacazul mail read <id>       # prints the message and marks it read
jacazul mail reply <id> --body-file answer.md
```

`read` marks the message read for the reading session only, so a message to
a whole project stays visible to its other sessions until each one reads it.

## Storage

```text
~/.jacazul/mail/<PROJECT_ID>/
|-- inbox/<id>.json        # one file per message
\-- read/<SESSION_ID>/<id> # empty marker: this session read it
```

A message file:

```json
{
  "id": "20261026T233512Z-6f1c",
  "from": {"project": "jacazul-ai_launcher", "session": "0989a06c",
           "persona": "arnalbam", "harness": "claude", "model": "claude-opus-5-5"},
  "to": {"project": "jacazul-ai_flow", "session": ""},
  "created": "2026-10-26T23:35:12Z",
  "subject": "Library API for opening storage",
  "refs": ["task:c3292d7b", "ticket:#144", "commit:6af396e"],
  "reply_to": "",
  "body": "..."
}
```

- Writes are atomic: write a temporary file in the same directory, then
  rename. Concurrent senders never see a half-written message.
- The ID is generated by the launcher (timestamp plus random suffix) and
  validated on read; a file name is never built from message content.
- Directories are `0700`, files `0600`.
- Read messages older than a retention period (30 days, open question) are
  removed by the launcher bootstrap, like expired cache sessions.

## Waking an idle agent (optional adapters)

The core never wakes anyone: an idle agent reads its mail on its next
workflow command. An operator who wants a nudge enables one adapter:

- **tmux:** `send-keys` a fixed line ("You have mail: run jacazul mail
  list") into the receiver's pane. Never the body.
- **Claude Code:** its cross-session message, where both ends run Claude
  Code.

An adapter only ever points at the mailbox; the message itself is always
read through `jacazul mail`, so every harness sees the same content.

## Security

- Mail is local to one user's home; nothing leaves the machine.
- The body is untrusted input for the receiver: it is shown as data and
  never executed, sourced, or treated as an instruction that overrides the
  receiver's rules. A peer asking for an action the receiver's session
  would block is surfaced to the operator, not performed.
- No secrets in bodies. `jacazul mail send` warns when the body matches a
  token or key pattern, like the security-expert light checklist does.
- A size limit (64 KiB, open question) keeps a message a pointer to work,
  not a payload; large content goes in a file in the project and is referred
  to by path.

## Rejected paths

- **Cross-project Taskwarrior annotations:** writing into another project's
  silo breaks project isolation.
- **A harness channel as the core:** works in one harness only.
- **A socket or daemon:** needs a running listener per session, does not
  survive restarts, and still cannot wake a harness that is waiting for
  input.

## Open questions

1. Retention period for read messages, and whether unread ones ever expire.
2. Size limit.
3. Whether the mailbox belongs to the launcher (`jacazul mail`) or to the
   flow engine once `tw-flow` is cut over.
4. Broadcast to every project of an organization, or only one project at a
   time.

## First slice

1. `jacazul mail send`, `list`, `read` and `reply` with the storage above,
   tested in a temporary home.
2. The `📬` banner in `tw-flow status` and onboard.
3. A collaboration protocol section in the `jacazul-engine` templates:
   when to send, that decisions are recorded as notes, and that a message
   is never approval.
